# MCP Invocation Coverage

Tool discovery alone does not establish that every advertised operation can actually run. The release verifier now observes successful calls made with the official SDK and requires each discovered tool name to have a successful standalone invocation.

`tests/mcp-command-catalog.test.ts` exercises every shared editing command through its individually registered MCP schema. The catalog is compared with the fixture inventory, so a newly registered command without a case fails the test. Each case uses real imported assets and an isolated SQLite project, performs an actual change, compares the MCP result with HTTP state, and verifies exact content restoration through undo. The fixtures prepare prerequisites through the same public protocol. Detailed animation, geometry, synchronization and visual correctness remain the responsibility of the corresponding domain and browser tests.

`tests/mcp-service-catalog.spec.ts` covers non-command service tools using real rendering, media, persistence and review operations. It now also exercises chunked imports, owner review details, history status, actual connected workspaces, viewport PNG/inspection and headless observation/contact diagnostics. Each principal is checked against its own discovered catalog; owner and guest permissions are not inferred from a shared tool name. New tools must have successful actual calls before the catalog test can pass.

The earlier module run invoked 39 owner services, three reviewer tools and the viewer's read tool successfully, producing synthesized WAV, Rhubarb cues, Rapier keys, a 72-frame 720p24 H.264/AAC video, a matching PNG, a restored project package and scoped comments. Its measured preview-to-video SSIM was 0.999774. Those counts and media measurements belong to that historical run.

Candidate 10's [current coverage report](../.data/full-delivery/final-candidate-10/checks-completion/mcp-coverage-current.json) records 927 SDK audit entries, 888 successful calls and 23 failed calls, retaining intentional error-path checks. Every one of the 165 distinct tool names discovered across owner/reviewer/viewer scopes has a successful standalone call; no prior-run audit records were copied into this count. The owner endpoint itself contains 164 tools. The service subset independently verifies 53 owner, three reviewer and one viewer operations, preserving each principal's permission checks.

The [completion report](../.data/full-delivery/final-candidate-10/checks-completion/verification-completed.json) binds this audit to source `df0bdc0861b797fb24fdd4cf2b73ffba689826c05d9297648cc7d69b728c2b90`, with all 326 source and eight built files unchanged. The first production catalog attempt omitted the native Rhubarb path and correctly reported unavailable; its failure remains in the original report. The explicit environment-corrected catalog rerun passes. The production suite therefore has 19 unique passing cases across the initial 18 successes and the corrected catalog, not a newly run clean 19/19 invocation.

The user's requirement is **all Web capabilities through MCP**, including the full supported file sizes and actual selection/view/playback state. [web-mcp-parity.md](web-mcp-parity.md) maps those capabilities to tools and behavioral checks. Successful invocation counts are an additional gate, not a substitute for that matrix or four actual film-package restorations through MCP.

`scripts/mcp-audit.mjs` is an opt-in Node preload used only by release verification. `WHITEFRAME_MCP_AUDIT_OUT` selects the JSONL output. It observes SDK calls without replacing their implementation or result, and records tool/schema names, success flags and hashes rather than argument content, credentials, images or media. Failed calls remain visible. Successful `edit_batch` members are counted separately and cannot satisfy a standalone tool's schema gate.

`scripts/summarize-mcp-audit.mjs INPUT.jsonl OUTPUT.json` produces a per-tool inventory with successful direct calls, successful batch dispatches, observed failures and missing coverage. `scripts/verify-release.mjs` runs this after the engineering checks and fails its `mcp:coverage` gate if any discovered tool lacks a successful direct call. Counts supplement behavioral assertions and rendered-artifact inspection; they do not replace either.

The candidate 04 frozen-source verification passes this gate after all 291 domain/service, 76 browser and 12 production-build checks. Its [coverage report](../.data/full-delivery/final-candidate-04/checks/mcp-coverage.json) summarizes 887 SDK audit records and all 151 distinct discovered tool names, with no missing successful standalone invocations or operations.
